# Emscripten patches

Fixes to nixpkgs' Emscripten (6.0.9) that the toolchain carries until a release has them. Each one is tracked upstream:
by an issue or pull request where one exists, and otherwise by a draft report under `docs/upstream/`, whose issue number
goes into the patch header once it is filed.

They are a stack: each applies exactly (no offset, no fuzz), with `patch -p1` or `git apply`, on top of nixpkgs' own
Emscripten patches and every lower-numbered one. Several touch the same files, and the later Node backend ones build on
earlier ones: 0012 and 0013 extend 0010's handling of a newly created file, and 0012's `doOpen()` change sits next to
0007's. To drop one, regenerate the ones above it.

nixpkgs installs the patched source tree whole under `share/emscripten`. The system libraries the frozen cache compiles
(`system/lib/wasmfs`, ...) and the JavaScript libraries every link reads (`src/lib`) both come from there, so changing a
patch rebuilds the cache and everything in `pkgsWasm`. `checks.emscripten-fixes` checks the behaviour each fix restores.

As of 6.0.11 (marked released 2026-10-02) #27632 (0001, since 6.0.10) and #27842 (0004) are in a release, and #27862
(0016) is on `main` for the next one. Checked against `main` 5977ecc on 2026-10-02: 0001 and 0004 reverse-apply, the
rest apply in order without 0001, 0004 and 0016 with offsets only, and the suite-format tests of 0014, 0015, 0018 and
0019 fail on `main` and pass with that stack (each draft's status, and `docs/upstream/README.md`).

0021–0024 apply on `main` 0479680 (2026-10-12) after 0002, 0003, 0005–0015 and 0017–0019, with offsets only.

0014 changes `src/lib/libpthread.js` and `system/lib/pthread`, so every threaded link and the libc the cache builds
carry it. A thread that ends unjoined adds itself to a lock-free list and wakes the main thread, which drains the list
in `emscripten_main_thread_process_queued_calls()`; the message to its event loop is still sent, for a main thread that
is idle there. Since a wait on the main thread can now free a thread, `dlopen()`'s sync, which lists the threads and
then proxies to each in turn, holds those cleanups off until it is through the list, then runs them; a proxy can wait
between checking the list and touching a thread. A sync that ends in an exception releases the hold without running
them. `checks.emscripten-fixes` runs rounds of such threads under a blocked main thread and checks that neither memory
nor Workers grow, and has a thread end while the sync is held up on another thread and while it waits on the dlopen
queue's mutex; the thread must not be freed until `dlopen()` is done. On Emscripten's own test runner, a 198-test
pthread selection under Node gives the same results with and without it. Both drafts carry tests in the suite's format,
also as `*.tests.patch` beside them.

0015 is independent of 0014 (it applies to 6.0.9 alone) but sits on top of it, since both change `libpthread.js`,
`library_pthread.c` and `threading_internal.h`. 0014 makes its race likelier: joins on other threads now clean up as
early as joins on the main thread always did. `checks.emscripten-fixes` reproduces the race: it joins a thread on the
main thread, creates a new one at the same address before the event loop runs, then `dlopen`s a side module the new
thread calls into.

0016 changes only emcc's link (`tools/link.py`, `tools/building.py`) and the setting's documentation (`src/settings.js`
and the settings reference generated from it). With `IMPORTED_MEMORY` and a `MAXIMUM_MEMORY` set on the command line, a
link without growth passes `--max-memory` to `wasm-ld` instead of `--no-growable-memory`; everything else is as without
growth: `emscripten_resize_heap()` fails or aborts, `getHeapMax()` is the memory's size, a memory Emscripten makes
itself has its maximum at its initial size, and `CAN_ADDRESS_2GB` follows the maximum as it does with growth.
`checks.emscripten-fixes` links with `-Werror=unused-command-line-argument`, which the unpatched warning fails, gives
the module memories of the initial size, between it and the maximum, and the maximum, and checks the heap spans each on
every thread and an allocation past it fails without growing it; a memory above the maximum is a `LinkError`. Its draft
carries `other.test_imported_memory_maximum_no_growth` in the suite's format (also as `*.tests.patch` beside it), which
fails on stock 6.0.9 and passes with the stack; the 202-test pthread selection gives the same results with 0016 as
without it.

Tested beyond `checks.emscripten-fixes`, with the whole stack on Emscripten's own test runner:
`other.test_gen_sig_info`, `other.test_wasmfs_getdents_node` and `wasmfs.test_fcntl_open_{nodefs,rawfs}` pass, and a
96-test WasmFS selection (stat, chmod, utime, access, links, `fcntl_open`, readdir, `unistd_*`, `other.test_wasmfs_*`,
...) gives the same results as unpatched 6.0.9. `test_stat_chmod`, which skips on WasmFS with the Node backend, gets
past its write-only (`0200`) `O_WRONLY` open with 0023 when un-skipped, and fails further on: it expects
`fchmodat(AT_SYMLINK_NOFOLLOW)` of a symlink to fail with `ENOTSUP` there, as NODEFS and NODERAWFS do, and WasmFS
changes the link instead.

0011 goes further than its draft's first, files-only hunk: a renamed directory's loaded descendants are rewritten too,
with the moved file and every loaded file below it locked (each before its children) across the host's rename. An
operation already holding one of those files finishes on the old path first; one that starts afterwards sees the new
one. It adds `Directory::getLoadedChildren()` to `file.h` to reach the dcache, which is private to `Directory`.

0012 and 0013 are carried together: with 0013 alone, making a directory with its parents was seen to fail with `EIO`.
0013 changes WasmFS's record of a mode or time only once the host has accepted the change; an omitted time
(`UTIME_OMIT`) is read back from the host and set again, since Node can't leave one alone. Symlinks themselves aren't
covered.

0017 gives `insertSymlink()` the `MaybeFile` return 0012 gave the other inserts, so it sits on 0012. A backend that
returns plain null still gets `EPERM`, which is what `symlink()` says for a file system without symlinks, and the OPFS
backend, which has none, now says so itself. `checks.emscripten-fixes` makes a symlink in a directory the host won't let
it write and expects `EACCES`.

0018 changes `system/lib/wasmfs/thread_utils.h`, which backends include, and `src/lib/libwasmfs.js` (with the new
import's signature in `libsigs.js`). A Worker hosts one thread at a time, so the heartbeat's timer is kept in one
variable per Worker. `~ProxyWorker()` clears it with a synchronous call proxied to the thread, the only one that can
reach its Worker's timers, before it cancels and joins the thread, so no tick can follow the queue being freed. The
thread runs its queue only from its event loop, which it enters after starting the heartbeat, so the stop can't come
before the start; it does wait behind whatever the thread is running, so the destructor lets that work finish before it
cancels the thread. While the program runs, that destructor is the only way a ProxyWorker's thread ends; at exit the
runtime terminates the Workers. `checks.emscripten-fixes` destroys a `ProxyWorker` and leaves its Worker idle, then busy
with other threads, for several heartbeats each; unpatched, the first tick on the idle Worker fails
`emscripten_proxy_execute_queue()`'s `pthread_self()` assertion, every time.

0019 gives `Directory::getChild()` and its handle the `MaybeFile` return 0012 gave the inserts, so it sits on 0012
and 0017. Null with no error code still means there is no such file, so a backend that returns plain null behaves as
before. Path lookup, `unlinkat()`, the unmount syscall and `rename()` pass a backend's error on; `open()`, `mkdir()`,
`symlink()` and `rename()`'s target fail with it instead of taking the file for missing. `FS.writeFile` fails instead of
creating the file, but without the code: `_wasmfs_write_file` returns 0 for any failure. The Node backend's
`_wasmfs_node_get_mode` now returns the host's errno, or `EIO` for a host code with none (`src/lib/libwasmfs_node.js`);
its signature is unchanged. The preload loop in `wasmfs.cpp` still only asks whether a child exists. It runs at
start-up, before anything is mounted, so it only looks in the root directory's backend, the memory backend unless a
program supplies its own root, whose lookups can't fail. The IndexedDB backend relies on it so that a lookup in a closed
database is `EIO`, never `ENOENT`. `checks.emscripten-fixes` looks up a file in a directory the host won't let it
search, with `stat()` and `open()`, and expects `EACCES`; its draft carries `other.test_wasmfs_node_lookup_errors` in
the suite's format (also as `*.tests.patch` beside it), which fails on stock 6.0.9 and passes with the stack.

0020 changes only JavaScript: `src/shell.js`, `src/shell_minimal.js`, `src/runtime_debug.js` and
`src/lib/libnoderawfs.js`, and adds `src/node_shell_write.js`, which both shells include for Node builds with threads or
NODERAWFS. Node constructs a Worker with its stdio forwarded through `process.stdout` and `process.stderr`, and opening
those makes a pipe or socket under them non-blocking for the whole process. `out()` and `err()` write their whole line,
sleeping 1 ms with `Atomics.wait()` whenever the write comes up short or fails with `EAGAIN`; NODERAWFS's `write()` does
the same on `EAGAIN` unless the program set `O_NONBLOCK` on the stream, and passes a short count on to its caller. A
line's first write hands `fs.writeSync()` the string itself, which is what the worker-host and runtime tests' captures
of fds 1 and 2 intercept. `checks.emscripten-fixes` writes 1.25 MiB to stdout and to stderr, from the main thread and
from a pthread, on Emscripten's JavaScript file system, WasmFS and NODERAWFS, with neither stream read for the first
half second, and expects every byte and status 0; unpatched, each of the twelve fails.

0021 changes `src/lib/libpipefs.js` and, in WasmFS, `file.h`, `pipe_backend.h` and `syscalls.cpp`. A blocking writer
can't wait for a reader, so it still queues everything; only a writer with `O_NONBLOCK` is held to the capacity, with
`PIPE_BUF`'s rule that a write of up to 4096 bytes goes in whole or fails with `EAGAIN`, and a larger one is cut short
at the room left. `poll()` reports the write end writable only while a `PIPE_BUF` write fits, on both file systems, so a
writer that polls before each write stops at the capacity whether or not it is non-blocking (GLib's `/mainloop/unix-fd`
fills a pipe that way), and a PIPEFS read wakes a writer waiting in `poll()`. WasmFS's `DataFile` gains a
`getWriteRoom()` hook beside 0003's `isReadReady()`, which pipes implement; the syscall layer, which has the open file's
flags, applies it to `write()` and `writev()` as a whole. Its JavaScript write check is the one #27831 suggests; the
`poll()` side and WasmFS's half go further than the issue. `checks.emscripten-fixes` runs the same cases on WasmFS and
on NODERAWFS, whose pipes are PIPEFS: a non-blocking fill stops at 64 KiB with `EAGAIN`, a large write is cut short, a
small one that doesn't fit is refused whole, and `poll()` follows the room while a blocking writer overfills.

0022 changes only `PIPEFS.stream_ops.read`, exactly as the comment on #26708 suggests. WasmFS's pipes already read 0
there; they read 0 also while a writer is open, which this leaves alone. `checks.emscripten-fixes` reads a pipe to its
end on both file systems.

0023 sits on 0010, whose `NodeState::open()` it changes. `_wasmfs_node_open()` takes the access mode (`O_RDONLY`,
`O_WRONLY` or `O_RDWR`) in place of a mode string, so its signature in `libsigs.js` changes, and passes Node's own
constants to `fs.openSync()`. An open that needs more access than the host descriptor already shared by the file's other
opens still reopens it read-write. `checks.emscripten-fixes` makes a file write-only and opens it with `O_WRONLY`;
unpatched, the host refuses with `EACCES`.

0024 changes `system/lib/wasmfs/special_files.cpp`, `wasmfs_internal.h` and `src/lib/libwasmfs.js` (with the new
import's signature in `libsigs.js`). Each line goes to `out()` or `err()` with its length, through
`UTF8ToString(..., ignoreNul)`, so a NUL byte reaches the console as one; `flush()` writes the buffered line instead of
a NUL. The streams stay a line-buffered text console: bytes that aren't UTF-8 are replaced, and `out()` ends a last line
without a line break with one. Programs linked without a file system (`libwasmfs_no_fs`) print through the JavaScript
`fd_write`, which still breaks lines at a NUL. `checks.emscripten-fixes` writes a NUL inside a line to stdout and to
stderr and expects it back.
