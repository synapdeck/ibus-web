# M0.5: WasmFS IndexedDB backend — implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Finish M0 with the runtime's storage (spec §5.6): our own WasmFS
backend over IndexedDB, full lazy — files stored as `ArrayBuffer` chunks and
read and written a chunk at a time on a backend thread — mounted at
`/engines/<name>/` in browsers, WasmFS's Node backend in its place under
Node, engine data installed into it once per version, and one writer per
engine's user data across tabs.

**Architecture:** A new runtime part, `runtime/wasmfs-idb/`: a C++ WasmFS
backend compiled against the patched Emscripten's internal headers
(`-I<emscripten>/system/lib/wasmfs`, from the same tree the cache was built
from) plus an Emscripten JS library passed with `--js-library`. Every backend
call is proxied to one backend thread (`emscripten::ProxyWorker`, a pool
pthread that lives in its JS event loop), where the JS library talks to
IndexedDB and finishes the proxied call with `_emscripten_proxy_finish`.
Writes are write-through: each `write()` commits in one IndexedDB
transaction before returning. A reusable Playwright runner, `tests/browser/`,
runs C test programs in Chromium and Firefox; the R2/R3 spike harness
measures the backend under the page's spin. The backend is written to be
submitted upstream later as `wasmfs_create_idb_backend`.

**Tech Stack:** Nix flake (flake-parts, import-tree), Emscripten 6.0.9 plus
`modules/emscripten/patches` (0001–0016), WasmFS internals, C++17, C,
TypeScript (pnpm 11), Playwright 1.61.1 with nixpkgs' Chromium and Firefox,
Node 24.

## Reference: what the backend plugs into (Emscripten 6.0.9 with our patches)

Paths are relative to the patched Emscripten tree (`<emscripten>/share/emscripten`; get it with `nix eval --raw .#legacyPackages.x86_64-linux.emscriptenCache.emscripten`).

- **Backend API** (`system/lib/wasmfs/backend.h`, `file.h`): `Backend::createFile/createDirectory/createSymlink`; `DataFile::open(oflags)` (flags are only `O_RDONLY`/`O_WRONLY`/`O_RDWR`; every fd open calls `open`, the fd's last close calls `close`; files stay usable while open even if unlinked), `close`, `read(buf, len, off)`, `write(buf, len, off)` (short counts allowed, negative errno on error), `getSize` (may be called unopened), `setSize` (may be called unopened; growth zero-fills), `flush` (what `fsync`/`fdatasync` call; `close` does not flush), `isReadReady`; `File::setMode`/`setTimes` (patch 0013; persist them, return non-zero to refuse); `Directory::getChild` (null = ENOENT), `insertDataFile`/`insertDirectory` (return `MaybeFile`, patch 0012), `insertSymlink`, `insertMove` (may overwrite; failure changes nothing; a foreign-backend file gives `-EBUSY`), `removeChild` (0 if already gone), `getNumEntries`, `getEntries`, `maintainsFileIdentity` (keep `false`: WasmFS's dcache keeps identity). `mode`, `atime`, `mtime`, `ctime` live in `File` in memory and are set to now at construction: load the stored values when constructing.
- **Locking:** every backend method is called with that file's recursive mutex held, and the calling thread blocks while the call is proxied, so code on the backend thread must never call back into WasmFS syscalls or take file locks; it may call exported helpers that only touch a `std::vector` (as OPFS's `_wasmfs_opfs_record_entry` does). Calls from several pthreads queue concurrently on the backend thread, so the JS must tolerate overlapping async operations on different files.
- **Template:** `system/lib/wasmfs/backends/opfs_backend.{cpp,h}` (418 + 107 lines), `src/lib/libwasmfs_opfs.js` (474), `system/lib/wasmfs/thread_utils.h` (`ProxyWorker`, 107): one `ProxyWorker` per backend; async JS imports take a `ProxyingCtx` and out-pointers and end with `_emscripten_proxy_finish(ctx)` (`__deps: ['emscripten_proxy_finish']`); JS objects in `HandleAllocator` tables (`src/lib/libcore.js`, ids from 1) in the backend thread's realm; DOMException names mapped to `-errno`; `__i53abi` functions need an explicit `__sig` in our own library.
- **Mounting:** `wasmfs_create_directory(path, mode, backend)`; backends are never destroyed. Construct with `wasmFS.addBackend(std::make_unique<Backend>(…))` (`system/lib/wasmfs/wasmfs.h`).
- **Linking out of tree:** compile with `-I<emscripten>/system/lib/wasmfs -std=c++17` plus `commonFlags`; link the runtime and tests with `--js-library=<path>/libwasmfs_idb.js`. The headers must come from the same patched tree the cache was built from (patches 0003/0011/0012/0013 change `file.h`'s virtuals).
- **Node backend:** `wasmfs_create_node_backend(root)` maps a WasmFS directory to a host directory, runs `fs.*Sync` on the calling thread (no proxying, no pool thread), works from pthreads under `worker_threads` (spike), persists to the host. Remaining limits: sizes are `uint32`, `O_WRONLY` opens `"r+"`, no symlink creation.
- **Tests to model on:** `test/wasmfs/wasmfs_opfs.c` (setup/resume persistence across two runs), `wasmfs_opfs_errors.c` + `_post.js` (another holder forcing errors).

## IndexedDB layout (fixed here; later tasks rely on it)

One database per backend instance, named by the caller. Version 1. Object stores:

| Store     | Key                 | Value                                                                                                                                                                                                                                  |
| --------- | ------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `meta`    | string              | `"format"` → `1`; `"chunkSize"` → bytes (fixed when the database is created); `"nextIno"` → next inode number; `"root"` → the root directory's inode number; `"installed"` → `{ version, files, bytes }` once engine data is installed |
| `inodes`  | inode number        | `{ kind: 1 file / 2 directory / 3 symlink, mode, size, atime, mtime, ctime, target? }` (times in ms)                                                                                                                                   |
| `entries` | `[parentIno, name]` | child inode number (a directory's entries are the key range `[[p, ""], [p, "￿"]]`)                                                                                                                                                     |
| `chunks`  | `[ino, index]`      | `ArrayBuffer` of at most `chunkSize` bytes; a missing chunk reads as zeros (sparse); the last chunk may be short                                                                                                                       |

Inode 1 is the root, created with the database. Unlinking removes the entry; the inode and its chunks are removed when it has no entry and no open handle in this runtime (orphans left by a crash are removed when the backend starts: inodes with no entry). Every operation that touches more than one record runs in one transaction.

## C API (fixed here)

```c
/* ibus-web/wasmfs-idb.h */
#include <emscripten/wasmfs.h>

/* Opens (creating if needed) the IndexedDB database `database` and returns
 * a backend whose root is that database's root directory. Must be called on
 * a pthread or a Worker's main thread, never the browser's main thread.
 * Returns NULL if IndexedDB is unavailable or the database can't be opened.
 */
backend_t wasmfs_create_idb_backend(const char *database, uint32_t flags);

/* The backend refuses every change with EROFS. */
#define WASMFS_IDB_READ_ONLY 0x1u
```

### Task 2: The backend: files, directories, persistence

**Files:** `runtime/wasmfs-idb/{package.nix,checks.nix}`, `include/ibus-web/wasmfs-idb.h` (the C API above), `src/idb_backend.h`, `src/idb_backend.cpp`, `src/libwasmfs_idb.js`, `tests/basic.1.c`, `tests/basic.2.c`, `runtime/options.nix` (`ibusWeb.runtime.wasmfsIdb`: the package, with `passthru.jsLibrary` and `passthru.cflags` holding the `-I` for WasmFS's internal headers, derived from `ibusWeb.toolchain.emscripten`).

**Requirements:**

- The layout and C API above, exactly. `IdbBackend` owns one `ProxyWorker`; `IdbFile`, `IdbDirectory`, `IdbSymlink` hold the inode number and the backend; every operation is one proxied call to an async JS import that runs one IndexedDB transaction and finishes the call.
- Files: `open`/`close` (track open counts so an unlinked open file stays readable until its last close, then its inode and chunks are deleted), `read`, `write` (write-through: one read-write transaction over `chunks` and `inodes` that reads the edge chunks it partly overwrites, puts the new chunks, updates `size` and `mtime`, and completes before `write` returns), `getSize`, `setSize` (truncation deletes chunks past the end and trims the last; growth just updates `size`, since missing chunks read as zeros), `flush` (Task 4), `setMode`/`setTimes` (persisted).
- Directories: `getChild`, `insertDataFile`, `insertDirectory`, `insertSymlink`, `insertMove` (same backend only; overwrite semantics as POSIX `rename`; one transaction), `removeChild`, `getNumEntries`, `getEntries` (entries pushed into the C++ vector through an exported `_wasmfs_idb_record_entry`, as the OPFS backend does).
- Errors: IndexedDB `QuotaExceededError` → `-ENOSPC`; `ConstraintError` → `-EEXIST`; `ReadOnlyError` and the read-only flag → `-EROFS`; `VersionError`/`InvalidStateError` (connection closed) → `-EIO`; anything else → `-EIO`.
- Values are `ArrayBuffer`s (copy out of WASM memory with `slice`, never store a view of the shared memory).
- `tests/basic.1.c`: mount at `/data`, mkdir, create, write across a chunk boundary, lseek/read back, stat, getdents, rename (file and directory), unlink, rmdir, a file kept open after unlink. `tests/basic.2.c` (same browser context, next run): the expected files exist with their contents, sizes, modes and mtimes.

### Task 4: Durability, metadata, upgrades, errors

**Files:** `src/libwasmfs_idb.js`, `src/idb_backend.cpp`, `tests/fsync.c`, `tests/errors.c`, `tests/errors-post.js` (a `--post-js` that holds a conflicting connection or forces a version change).

**Requirements:**

### Task 6: Installing engine data once per version

**Files:** `runtime/libibus-web/{include/ibus-web/runtime.h,src/install.c,tests/…}`, `tests/spikes/runtime/src/worker/host.ts`, scenarios, a test archive built in Nix.

**Requirements:**

- Archives are uncompressed POSIX ustar (compression is the HTTP layer's job); `libibus-web` gains a streaming extractor that writes through the mounted file system, so the storage layout has one writer:
  ```c
  typedef struct _IBusWebInstall IBusWebInstall;
  /* Starts extracting into `dir` (which must exist). */
  IBUSWEB_API int ibusweb_install_begin (const char *dir, IBusWebInstall **out);
  /* Feeds the next `len` bytes of the archive; returns 0 or a negative errno. */
  IBUSWEB_API int ibusweb_install_feed (IBusWebInstall *install, const uint8_t *data, uint32_t len);
  /* Finishes: fsyncs what it wrote, returns 0 or a negative errno, frees `install`. */
  IBUSWEB_API int ibusweb_install_end (IBusWebInstall *install);
  ```
  Regular files and directories only; anything else, absolute paths and `..` are refused with `-EINVAL`. GTest cases in `libibus-web` cover it on the memory backend.
- The host installs at engine start, before the engine accepts requests: it takes a Web Lock (`navigator.locks.request("ibus-web:install:<name>", …)`), checks `meta.installed` (exposed through a backend query or a marker file `/engines/<name>/.installed` written last — choose and say why), and if absent or older streams the fetched archive (`response.body` reader) into `ibusweb_install_*` in pieces, writes the marker last, releases the lock. A second tab waiting on the lock sees the marker and skips. An interrupted install leaves no marker and is redone. (In Firefox the response body waits while the page spins; install is off the request path, so that only delays startup.)
- Scenarios: `install-fresh`, `install-skip` (second context in the same profile sees it installed), `install-concurrent` (two Workers start at once; one installs, the other waits and skips), `install-interrupted` (kill the Worker mid-install; the next start redoes it).

## Known gaps and follow-ups

Where the build departs from this plan (the spec's §5.6 has the design as
built):

- **Engine data has a database per version**, `ibus-web/<name>/data/<V>`,
  not a place in the engine's own database: an upgrade that shared it left
  an older host reading a half-new tree, and dropped or retyped paths
  survived. Locks are per version (`ibus-web:data:<name>:<V>` shared for a
  host's life, `ibus-web:install:<name>:<V>` exclusive); the writer lock
  covers the engine's own files only; other versions are collected through
  `indexedDB.databases()`, so the toolchain's minimum Firefox is 126 (a
  one-way floor over Baseline). Hence the pool's storage share is 2.
- **The C API has two more calls**: `wasmfs_idb_backend_seal()`, which the
  installing host calls once the marker is durable, and
  `wasmfs_idb_backend_closed()`, which the host polls to report
  `storage: closed`.
- **`fsync()` puts the inode back** inside its strict transaction: an empty
  strict transaction syncs nothing in either browser (`strace`). Chunks are
  16 KiB, and at most 63 KiB, since Chromium stores larger values as Blobs.
- **Three Emscripten patches**: 0017 (a backend's symlink errors reach the
  caller), 0018 (a `ProxyWorker`'s heartbeat stops before its thread) and
  0019 (a backend's lookup errors reach the caller, so a lookup in a closed
  database is `EIO`, not `ENOENT`).
  The toolchain's wrapper now gives a link only the minimum versions of the
  environments its `-sENVIRONMENT` allows.

What M1 inherits:

- **The storage protocol lives in the spike host.** `@ibus-web/worker-host`
  takes it over from `tests/spikes/runtime/src/worker/host.ts`: the probe
  that doesn't create the database, the writer lock taken before the user
  backend exists, the data and install locks with their 1 s request rounds
  (Node grants a queued request late) and the progress channel, the marker
  read before mounting, deletion, install, the strict marker and the seal,
  collection of old versions, every lock in one set let go on a failed
  start, the user backend sealed before the writer lock goes, and the
  `storage` events. The page side takes the restart wait for
  a terminated writer's lock (`tests/spikes/runtime/src/page/page.ts`) and
  keeps out of engine databases.
- **Waking the host for `storage: closed`.** The host notices a closed
  connection only when it next wakes; a version change while the engine is
  idle goes unreported until a request or a GLib source. The relay could
  wake it, or the page could restart the Worker on its own `versionchange`.
- **A writer that unlinks a file another tab has open** deletes its inode at
  once: open counts are per connection, so the reader's next read fails
  with `ENOENT`. Harmless for engine data, which no one unlinks; user data
  that readers in other tabs keep open needs a rule before M4's user
  dictionaries.
- **Host API**: usage report, export and reset (spec §5.6), and the
  `storage` usage events §8 gives for quota, aren't built.
- **The backend's internals are runtime exports.** The helpers its
  JavaScript calls (`_wasmfs_idb_record_entry`, `_wasmfs_idb_set_string`)
  are `EMSCRIPTEN_KEEPALIVE`, so the runtime exports them; only the export
  manifest keeps side modules off them.
- **Restarts in Chromium.** A host that dies without the page terminating
  it gets no wait for its writer lock, so a restart within some 2 s may come
  up read-only for the Worker's life.
- **Node.** The Node backend has no read-only mode, so a read-only mount and
  a seal are conventions there, and Web Locks don't coordinate separate Node
  processes sharing a directory. The Node marker's directory sync swallows
  every error, an `EIO` included.
- **Runtime-level coverage in spike checks.** The storage scenarios (the
  mount, fallback, close, the thirteen install scenarios, `storage-costs`)
  move with the spike's other runtime coverage before `tests/spikes` goes,
  in M0.6.
- **Every test becomes structured** in M0.6: GTest for C and C++, Vitest
  for TypeScript. That covers `ibus-runtime`'s load harness
  (`tests/load.mjs`, `harness.mjs`) on Vitest, `checks.emscripten-fixes`'
  programs on GTest, and the spike checks' runtime coverage as it moves
  out; GLib's test gate (`gate.py`) and its tests (`gate-test.py`) rewritten
  in TypeScript on Vitest; checks whose only assertion is that something
  builds or links stay as they are. The browser test runner
  (`tests/browser`, `ibusWeb.testing.browserRun`) becomes a thin Vitest
  shim: it runs each WASM program in Chromium and Firefox, keeps the
  numbered programs' shared browser context, and turns the program's GTest
  results into one Vitest result per GTest case. The results come from
  GTest's JSON report (`--gtest_output=json:` to a file in the program's
  in-memory file system), which a hook in the shared test harness posts
  to the page at exit, so failure messages and timings arrive as data
  rather than parsed from stdout.
- **The backend's tests move to GTest** in M0.6, linked with
  `-sPROXY_TO_PTHREAD` so tests run on a pthread and the Worker's event loop
  stays free for IndexedDB events and post-js; persistence tests stay

Open, for later milestones:

- **WebKit's IndexedDB in Workers** is unchecked (spec R5, R13).
- **Real quota failures** aren't reached in tests; `errors.c` injects the
  state a quota failure leaves.
- **Measurements on one machine**: the fsync and storage figures come from
  one host's ZFS. Chromium's 64 KiB cliff is attributed to Blink's value
  wrapping from its size, not traced; Firefox's out-of-line threshold is
  measured (between 768 and 896 KiB), not read from its default.
- **Untested paths**: the 10 s limit on a blocked deletion (nothing in the
  runtime makes a connection that blocks one), a waiter's 120 s limit
  extended by progress (it needs an install longer than 120 s), and a stray
  `<V>.marking` under Node. The browser `install-torn-marker` case puts a
  non-marker value, since a browser's commit can't tear.
- **0018 off our backend**: the browser OPFS and fetch backends weren't run
  with it, and a `ProxyWorker` thread that ended other than through its
  destructor would still leave its timer (none can today).

Minor items left from the reviews:

- Backend: every `open()` costs one read-only transaction; the ordering in
  the open/unlink race is argued in a comment, not tested; a `pwrite()`
  straddling 2^53 − 1 fails whole with `EFBIG` rather than writing short.
- Installing: each read of the archive's response is one write, and so one
  write transaction; since the 512-byte ustar headers offset the data, most
  writes cover a partial chunk at each end and read those chunks first.
  Installing is off the request path; buffering the extractor's writes to
  chunk boundaries would remove the reads.
- Test hooks: the chunk counter doesn't count `getAllKeys()` or cursors, and
  a `get()` of a hole counts nothing; `chunk-counts.h` defines a non-static
  function and statics in a header; the injected delete fault aborts
  synchronously, as a body that throws rather than a commit that aborts.
- Library typing: an inline `$foo: () => {}` entry is rejected with a
  confusing message; the `.d.ts` decorator list is copied by hand; the
  negative type test repeats the tsconfig's options; the dev-shell entry
  runs a nested `nix build`, leaving a stale out-link if it fails; the
  check for function-looking strings reads its patterns from the one `if`
  in `jsifier.mjs` whose block assigns `isFunction`, assuming that shape;
  any failure while evaluating `addImplicitDeps` but a missing name gives
  one catch-all message.
- Browser runner: output a pthread prints just before exit can be lost
  (tests report through the exit code); C fixtures that aren't main modules
  link with `$CC`.
- Firefox warns that the legacy exception encoding is deprecated once per
  Worker that instantiates the module (spec R18): about 1,000 of a
  `runtime-spike-browser` run's 2,100 lines. The browser runners count the
  warning and print one line per page instead.
