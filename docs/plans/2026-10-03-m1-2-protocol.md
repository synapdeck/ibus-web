# M1.2: `@ibus-web/protocol` — implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A TypeScript package, `@ibus-web/protocol`, that is the source of truth for the
Worker-boundary protocol (spec §6.3): a GVariant codec for any signature, Effect Schema classes
for the IBus types, one schema per request and output record, and the framing. libibus-web's
`ibus-web/protocol.h` and the published protocol document are generated from those schemas. C
and TypeScript agree byte for byte, proven against the real runtime in WebAssembly. The decode
cost of a 500-candidate lookup table is measured.

**Architecture:** Three layers, as spec §6.3 has them. (1) `src/gvariant/`: a parser for GVariant
type strings, a tagged value tree, and a hand-written encoder and strict decoder between
`Uint8Array` and that tree, exposed as the schema codec `GVariantBytes(signature)`. It is the
only byte-level code. (2) `src/ibus/`: `Schema.Class`es for the IBus types built by a
`serializable(name, fields)` helper. Fields carry their GVariant type as an annotation, and one
AST walk derives both a schema's signature and its mapping to and from the tree. (3)
`src/messages/`: a `Schema.TaggedClass` per request and record, annotated with its `kind`, unions
by `kind`, and the framing (headers as data). Generators in `scripts/` print `protocol.h` and
`PROTOCOL.md` from layer 3; Nix's `files` writer commits them and fails a check while a tracked
copy differs. The C build never runs Node.

**Tech Stack:** TypeScript 7 (Node's type stripping for scripts), Effect 4.0 (`Schema`,
`SchemaAST`, `SchemaGetter`, `SchemaIssue`, `Arbitrary`, all from `"effect"`), Vitest 5 with
`@effect/vitest` (`it.prop`), tsdown, pnpm workspace built offline by Nix, the `files` flake
module, `pkgsWasm` with libibus-web and json-glib for the C side of parity, Node for running it.

## Decisions fixed here (later tasks rely on them)

**The schemas are the source of truth; `protocol.h` is generated.** Message names, kind numbers,
field names, field GVariant types and descriptions, the protocol version, the two headers'
layouts and the one flag are defined in TypeScript. `scripts/protocol-h.ts` prints the header
libibus-web installs today, with the same macro, struct, enum and function names, the same kind
numbers and the same signatures. The wire doesn't change: `IBUSWEB_PROTOCOL_VERSION` stays 1 and
`IBUSWEB_RUNTIME_ABI` stays as it is. Task 5 proves the switch by the C suites passing on the
generated header.

**Naming.** A message's class name is IBus's D-Bus member name (`ProcessKeyEvent`,
`UpdatePreeditText`, `SettingWritten`). Its C enumerator is the prefix plus the name in
screaming snake case: `IBUSWEB_REQ_PROCESS_KEY_EVENT`, `IBUSWEB_REC_UPDATE_PREEDIT_TEXT`. Field
names are camelCase in TypeScript; the C comments list them in order.

**Kinds.** Requests: lifecycle 1–4 (`Init`, `CreateEngine`, `DestroyEngine`, `SettingChanged`),
engine methods 16–31 as in today's header. Records: engine signals 1–15, runtime 32–33
(`SettingWritten`, `Log`), and 34, `Crashed`, reserved for the host: it is in the enum and in the
TypeScript kinds, with no schema and no signature-table entry, until M1.3 defines what the host
writes.

**The GVariant value tree** (`src/gvariant/value.ts`) is tagged by the type's first character, so a
decoder's output is self-describing apart from container element types, which the signature
gives:

```ts
export type GVariantValue =
  | { readonly _tag: "b"; readonly value: boolean }
  | { readonly _tag: "y" | "n" | "q" | "i" | "u" | "h" | "d"; readonly value: number }
  | { readonly _tag: "x" | "t"; readonly value: bigint }
  | { readonly _tag: "s" | "o" | "g"; readonly value: string }
  | { readonly _tag: "v"; readonly type: string; readonly value: GVariantValue }
  | { readonly _tag: "m"; readonly value: GVariantValue | null }
  | { readonly _tag: "a"; readonly items: readonly GVariantValue[] }
  | { readonly _tag: "()"; readonly items: readonly GVariantValue[] }
  | { readonly _tag: "{}"; readonly key: GVariantValue; readonly value: GVariantValue };
```

Dictionaries are arrays of `{}` nodes, so entry order survives a round trip. 64-bit integers are
`bigint`. Strings are JavaScript strings; the codec converts to and from UTF-8.

**The decoder is strict: it accepts exactly GLib's normal form.** Every input it accepts re-encodes
to the same bytes, with one exception: a NaN double's payload bits may not survive, since
JavaScript doesn't promise to keep them. Anything else that isn't normal form is a
`GVariantDecodeError`: nonzero padding, wrong fixed sizes, framing offsets out of order, out of
bounds or not of the minimal width, booleans other than 0 and 1, strings that aren't
NUL-terminated, contain NUL or aren't UTF-8, invalid object paths, signatures and variant type
strings, nesting deeper than GLib's 128. Records from the runtime are always normal form (it
writes them with `g_variant_get_data` of values it built), and the runtime rejects non-normal
requests (`EBADMSG`). Task 7 checks the decoder's judgement against `g_variant_is_normal_form` on
fuzzed bytes.

**Reference for the serialization:** the GVariant specification (Lortie, "GVariant Serialisation
Format", in GLib's documentation as `gvariant-specification-1.0`) and GLib's
`glib/gvariant-serialiser.c`, which is what `g_variant_is_normal_form` runs. In short:

- Alignment: `b y s o g` 1, `n q` 2, `i u h` 4, `x t d v` 8; arrays and maybes align as their element; tuples and dict entries as their most aligned member (an empty tuple 1).
- Fixed size: `b y` 1, `n q` 2, `i u h` 4, `x t d` 8; a tuple or dict entry whose members are all fixed-size is fixed-size, its members laid out with alignment and its end padded to its alignment, and `()` is 1 byte (zero). Everything else is variable-size.
- Strings: the UTF-8 bytes and a NUL. Variant: the child's bytes, a zero byte, then the child's type string without a NUL.
- Maybe: Nothing is empty; Just of a fixed-size type is its bytes; Just of a variable-size type is its bytes and a zero byte.
- Array of fixed-size elements: their bytes, back to back. Array of variable-size elements: each element aligned, then one framing offset per element (the end of each), little-endian.
- Tuple and dict entry: members in order, each aligned; for every variable-size member except the last, its end offset, stored in reverse order at the container's end.
- Framing offsets are 1, 2, 4 or 8 bytes wide: the smallest width whose maximum covers the container's whole size, offsets included. A container of size 0 has no offsets.

**IBus types** (from the vendored IBus 1.5.34 serializers). Every serializable is a tuple of its
type name, its attachments (`a{sv}`) and its own fields, in this order; nested serializables sit in
`v` slots:

| Class             | Signature            | Fields after `name`, `attachments`                                                                                                           |
| ----------------- | -------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| `IBusAttribute`   | `(sa{sv}uuuu)`       | `type`, `value`, `startIndex`, `endIndex`                                                                                                    |
| `IBusAttrList`    | `(sa{sv}av)`         | `attributes: IBusAttribute[]`                                                                                                                |
| `IBusText`        | `(sa{sv}sv)`         | `text`, `attrs: IBusAttrList`                                                                                                                |
| `IBusLookupTable` | `(sa{sv}uubbiavav)`  | `pageSize`, `cursorPos`, `cursorVisible`, `round`, `orientation`, `candidates: IBusText[]`, `labels: IBusText[]`                             |
| `IBusProperty`    | `(sa{sv}suvsvbbuvv)` | `key`, `type`, `label: IBusText`, `icon`, `tooltip: IBusText`, `sensitive`, `visible`, `state`, `subProps: IBusPropList`, `symbol: IBusText` |
| `IBusPropList`    | `(sa{sv}av)`         | `properties: IBusProperty[]`                                                                                                                 |

The name field isn't a class field: `serializable(name, fields)` writes it and checks it on
decode. Attachments are `Schema.Record(Schema.String, GVariantVariant)`. Indices are what IBus
sends (characters, not UTF-16 units) and attribute ends may be `0xffffffff` (IBus's `-1`); the
page converts. Enumerations IBus defines for these fields (`IBusAttrType`, `IBusOrientation`,
`IBusPropType`, `IBusPropState`, `IBusPreeditFocusMode`) are exported as `const` objects with
IBus's values; fields stay plain integers, since engines may send values a newer IBus defines.

**Dictionaries in schemas are records.** `Schema.Record(Schema.String, V)` derives `a{sV}`. JavaScript
orders integer-like keys first, so a record whose keys look like integers doesn't keep its entry
order; GSettings schema ids and keys and IBus attachment names never do. The tree layer keeps
order regardless.

**Public API** (`src/index.ts` exports exactly these, plus the classes and enums named above):

```ts
export const PROTOCOL_VERSION = 1;
export class GVariantDecodeError extends Data.TaggedError("GVariantDecodeError")<{
  readonly message: string;
  readonly offset: number;
}> {}
export class ProtocolError extends Data.TaggedError("ProtocolError")<{ readonly message: string }> {}
export const parseType: (signature: string) => GVariantType; // throws ProtocolError
export const encodeValue: (signature: string, value: GVariantValue) => Uint8Array;
export const decodeValue: (signature: string, bytes: Uint8Array) => GVariantValue; // throws GVariantDecodeError
export const GVariantBytes: (signature: string) => Schema.decodeTo<typeof GVariantTree, typeof Schema.Uint8Array>;
export const GVariantVariant: Schema.Codec<Extract<GVariantValue, { _tag: "v" }>>;
export const signatureOf: (schema: Schema.Top) => string;
export const Request = Schema.Union([Init, CreateEngine /* …every request class */]).pipe(Schema.toTaggedUnion("_tag"));
export type Request = typeof Request.Type;
export const OutputRecord = Schema.Union([CommitText, UpdatePreeditText /* …every record class */]).pipe(
  Schema.toTaggedUnion("_tag"),
);
export type OutputRecord = typeof OutputRecord.Type;
export const encodeRequest: (ic: number, request: Request) => Uint8Array; // header + payload
export const decodeRecord: (bytes: Uint8Array, offset?: number) => DecodedRecord; // one framed record
export interface DecodedRecord {
  readonly seq: number;
  readonly ic: number;
  readonly flags: number;
  readonly size: number;
  readonly record: OutputRecord;
}
export const requestKinds: ReadonlyMap<string, number>; // name → kind, from the annotations
export const recordKinds: ReadonlyMap<string, number>; // including Crashed
export const RECORD_CONTINUATION = 0x0001;
```

`size` is the record's framed size including padding, so a reader advances by it. Reassembling
`CONTINUATION` fragments is the ring reader's (M1.3); `decodeRecord` rejects a flagged record
with a `ProtocolError`.

### Task 7: C/TS parity

**Files:** `test/parity/{corpus.ts,write-corpus.ts,parity.test.ts}`, `test/parity/c/{parity.c,parity.gschema.xml}`, `module.nix`.

The pipeline is three derivations. (1) **Corpus:** `node write-corpus.ts $out` writes TypeScript's
encodings: `objects/<case>.bin` (IBus objects, top-level `(sa{sv}…)` tuples), `lifecycle/{init,create,destroy}.bin`
and `requests/<case>.bin` (framed requests), `fuzz/<case>.bin` with `fuzz.json` (signature per case: 500 byte strings over 20 types, drawn with
`Arbitrary.sampleEffect` from Task 2's `typeArbitrary` and `bytesArbitrary` with a fixed seed), and `cases.json` listing names and signatures.
(2) **C:** `parity.js`, built against libibus-web and json-glib, runs under Node with the corpus
and writes `$out`. (3) **Assertions:** `checks.protocol-parity`, a `testing.vitestCheck` of the
package with `IBUS_WEB_PROTOCOL_PARITY` set to a JSON file naming the corpus and C output
directories; `parity.test.ts` skips unless it is set.

**What the C program does** (`parity.c`, g_setenv'ing `GSETTINGS_SCHEMA_DIR` to its compiled
schema directory first):

- For each `objects/` case: `g_variant_new_from_bytes` with the case's signature; record `g_variant_is_normal_form`; `ibus_serializable_deserialize_object`; write the object's **projection** (below) to `ts-objects/<case>.json` and its re-serialization (`ibus_serializable_serialize_object`, `g_variant_get_data`) to `ts-objects/<case>.bin`.
- For each `fuzz/` case: write `{ "normal": g_variant_is_normal_form(...) }` per case to `fuzz.json`.
- Builds its own objects with IBus's API: texts (empty, ASCII, Hangul, an astral character, with underline and foreground attributes, one ending at `G_MAXUINT`), a lookup table of 500 candidates with labels and the cursor on page 3, properties with sub-properties, symbols, tooltips and an attachment, empty lists. Writes each as `c-objects/<case>.bin` and `.json`.
- Starts the runtime (`ibusweb_runtime_init`), registers a recording engine `parity` (`ibus_factory_add_engine`), dispatches the corpus's `lifecycle/init.bin` (a snapshot with one key of the parity schema) and `lifecycle/create.bin` (ic 1, engine `parity`), then every `requests/` case (each engine-method kind, 16–31, and `SettingChanged` on the parity schema), and `lifecycle/destroy.bin` last. Every request kind is thus TypeScript's bytes. It dispatches each case with `ibusweb_dispatch`, recording the return value and the arguments the engine's class handlers received (projections) into `requests.json`. The engine's `process_key_event` accepts `IBUS_a` (returns `TRUE`) and declines everything else, so the corpus has a `ProcessKeyEvent` case of each.
- Sends a `ProcessKeyEvent` of `IBUS_Return`, which the corpus never sends, whose handler emits every record kind once through IBus's emitters (`ibus_engine_commit_text`, `ibus_engine_update_preedit_text_with_mode`, `…_auxiliary_text`, `…_lookup_table`, the six show/hide calls, `ibus_engine_register_properties`, `ibus_engine_update_property`, `ibus_engine_forward_key_event`, `ibus_engine_delete_surrounding_text`, `ibus_engine_get_surrounding_text`), writes a key of `parity.gschema.xml` through `g_settings_set_string` (`SettingWritten`) and logs a `g_message` (`Log`). Writes the output buffer (`ibusweb_output_peek`) to `records.bin` and what it emitted, as projections in order, to `records.json`.

A **projection** is JSON built from IBus's public accessors only (`ibus_text_get_text`, the
attribute list's attributes, `ibus_lookup_table_get_*`, `ibus_property_get_*`, …), with IBus's
field names in camelCase, matching TypeScript's encoded form minus `_tag`. Attachments project as
the attachment names with their values' type strings. Writing JSON uses json-glib's builder and
generator: reuse the WebAssembly json-glib build `modules/engines/ibus-test.nix` makes, exposing it
through an `ibusWeb.*` option if it is a local binding there.

**Assertions** (`parity.test.ts`):

- every TypeScript object is normal form in C, C's re-serialization equals TypeScript's bytes, and C's projection equals TypeScript's encoded value;
- every C object decodes in TypeScript to its projection, and re-encodes to C's bytes exactly;
- every request returned what its case expects (0, or 1 for the `ProcessKeyEvent` cases the engine accepts) and reached the engine with the arguments TypeScript encoded;
- `records.bin` decodes record by record with `decodeRecord` (seq increasing from 1, ic 1, or 0 for `Log`), each record equal to its projection in `records.json`, and every record kind except `Crashed` appears;
- for every fuzz case, TypeScript's decoder accepts exactly when C says the bytes are normal form.

- [ ] **Step 2: Write `parity.c`** and the schema, and the three derivations in `module.nix`; build the C program the way `packages/worker-host/module.nix` builds `constants.js` (`$CC` with `pkg-config --cflags libibus-web ibus-1.0 json-glib-1.0`, `$CXX ${toolchain.testMainFlags}` with `--static --libs`), compiling the schema with `$($PKG_CONFIG --variable=glib_compile_schemas gio-2.0)`.
