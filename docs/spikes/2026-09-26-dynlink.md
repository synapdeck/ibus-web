# Dynamic-linking spike (M0.1)

- **Date:** 2026-09-26
- **Toolchain:** nixpkgs `8ce4ef6`, Emscripten 6.0.9, LLVM 22.1.8, Node v24.19.0
- **Build:** `nix build .#checks.x86_64-linux.dynlink-spike`

## Setup

Main module: C++, `-fPIC -pthread -fwasm-exceptions -O2 -sMAIN_MODULE=1
-sPTHREAD_POOL_SIZE=2 -sNODERAWFS=1 -sEXIT_RUNTIME=1`. Side modules:
`-sSIDE_MODULE=1` with the same compile flags, loaded with `dlopen` after the
thread pool exists.

## Results

| Side module | Result | Notes |
|---|---|---|
| side_basic | PASS | |
| side_thread | PASS | Ran on a pool thread created before the `dlopen`, with the pool pre-sized to 2 (`-sPTHREAD_POOL_SIZE=2`); no fallback to `-sPTHREAD_POOL_SIZE=0` was needed. |
| side_cxx | PASS | |
| side_throw | CAUGHT | Exception thrown in the side module propagated across the module boundary and was caught by `main.cpp`'s `catch (const std::exception &e)`; no abort, so no downgrade to a hard-failure expectation was needed. |
| side_hangul | PASS | |

Raw output:

```text
PASS side_basic.wasm
PASS side_thread.wasm
PASS side_cxx.wasm
CAUGHT side_throw.wasm: thrown in side module
PASS side_hangul.wasm
```

This is byte-for-byte identical to `tests/spikes/dynlink/expected.txt`.

The first build attempt, using the brief's `side_hangul.c` verbatim, failed
before reaching this output: `hangul.h` (from the wasm-built libhangul)
doesn't include a header that defines `NULL`, so the fixture's `if (hic ==
NULL)` failed to compile with `use of undeclared identifier 'NULL'`. Adding
`#include <stddef.h>` to `side_hangul.c` fixed it. This is a missing-include
bug in the fixture, not a dynamic-linking finding — it says nothing about R3.

Build warnings (present on the successful build, not failures): one
`em++: warning: dynamic linking + pthreads is experimental [-Wexperimental]`
from linking the main module, plus a `wasm-ld: warning: dynamic imports are
not yet stable` / `wasm-ld: warning: creating shared libraries, with -shared,
is not yet stable` pair from each of the five `-sSIDE_MODULE=1` links (10
`wasm-ld` lines total).

## Conclusions for the design

- **R3 is resolved: yes.** A threaded, `em++`-linked main module can `dlopen`
  side modules after its thread pool exists, run side-module code on a pool
  thread created before the `dlopen`, throw and catch a C++ exception inside
  a single side module, catch (in the main module) an exception thrown by a
  side module, and link a real static library (libhangul) into a side
  module. All five probes passed on the first successful build, matching
  `expected.txt` exactly; neither documented fallback
  (`-sPTHREAD_POOL_SIZE=0`, relaxing `side_throw`'s expectation to an abort)
  was needed. This confirms the design's basis for §5.4 on thread pools:
  engine side modules can be loaded after the runtime's thread pool exists.
  On exceptions, what was observed is narrower: one exception thrown in one
  side module was caught in the main module, with no nesting, no concurrent
  throws, and no throw across a C stack frame. Inference, not observation:
  this is not enough on its own to conclude that cross-module C++ exceptions
  in general need no design accommodation.
- **C++ exceptions work both within a side module and across the main/side
  module boundary**, using ordinary `throw`/`catch`, with no observed need
  for the runtime to install anything beyond standard C++ exception handling
  to make this work.
- **Toolchain facts affecting §5.3/§5.4** (observed during this and the
  preceding toolchain spikes, not part of the five pass/fail probes above):
  - A main module built with `-fwasm-exceptions` must be linked with `em++`,
    not `emcc`. Linking with `emcc` leaves libunwind's reference to
    `__gxx_wasm_personality_v0` unresolved. This fits §5.3's design: the
    runtime main module carries the C++ runtime (libc++, libc++abi) for C++
    engine side modules, and that carries the exception-personality
    dependency that only the `em++` driver resolves.
  - With `-fwasm-exceptions`, Emscripten 6.0.9 defaults to the legacy WASM
    exception-handling instructions (library variants named
    `*-legacyexcept`), not the newer exnref form. `-sWASM_LEGACY_EXCEPTIONS=0`
    selects exnref. Which form to ship is an open question that depends on
    target browser support; it is not decided by this spike and is left open
    for a later milestone.
  - Emscripten prints "dynamic linking + pthreads is experimental" when
    linking a main module with both `-sMAIN_MODULE` and `-pthread`. The spike
    passed all five probes despite this label, but it is upstream's own
    warning about the feature combination §5.3/§5.4 depend on, and belongs in
    R3's risk status rather than being dropped as noise.
- Nothing observed in this spike requires a change to §5.3 or §5.4 as
  written; the toolchain facts above are additional context for anyone
  revisiting those sections, not corrections to them.
