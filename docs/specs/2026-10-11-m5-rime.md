# M5: Rime

M5 ports ibus-rime, the IBus front end of the Rime input method engine, as one engine module, `rime`, with the
mainstream schemas of `rime-data` and `rime-ice`: simplified and traditional pinyin, double pinyin, Zhuyin, Cangjie,
Quick, Wubi, stroke, Cantonese and Shanghainese, each a page-side engine of its own. It is the project's only Chinese
engine (D2) and its first with threads of its own: librime's deployer and LevelDB's compaction.

Three things outside the module change for it. Before any of it, a comparison of Rime's long-sentence conversion with
ibus-libpinyin's settles R19, and with it whether libpinyin returns as M6. Engines gain data of their own, installed
when an engine is first made rather than when its module starts, so a Rime user downloads the dictionaries of the
schemas they use rather than all of them (R7). And ibus-rime registers Rime's option switches as IBus properties, so a
page can drive them from its own controls.

## Goals

- Every shipped schema typing in the browser through the existing router and panel, each as an engine the page can
  select by name.
- A decision on R19 from measured conversions, recorded in the design spec.
- Per-engine data: an engine's dictionaries fetched and installed the first time it is made, in any module.
- Rime's switches (simplified/traditional, full/half width, ASCII punctuation, ASCII mode) as properties a page can read
  and set without Rime's own menu, and Rime's own controls able to be turned off.
- Rime's settings through the page's settings like any other engine's, with no YAML on the page.
- A user dictionary that learns and survives restarts, on LevelDB over the IndexedDB backend.

## Non-goals

- A grammar model (`librime-octagram`'s `.gram`). `librime-octagram` is built, as nixpkgs builds it, but no schema uses
  it. RIME-LMDG's model is 398 MB, and its release is overwritten in place, so it can't be pinned.
- User-written YAML: patches beyond what the settings schema offers, custom phrases, and Rime's sync directories as a
  way to move data in or out.
- Shipping the niche `rime-data` schemas by default: the Array, combo pinyin, stenotype, IPA, Middle Chinese and the
  other dialect schemas, and the tone-marked variants beyond `terra_pinyin`. They build with one argument
  ([Selecting schemas](#selecting-schemas)), but neither the default distribution nor `@ibus-web/engine-rime` has them.
- Data from xddxdd's NUR. Nothing M5 ships needs it: nixpkgs now packages `rime-zhwiki`, and no schema here uses it. The
  flake input waits until some data needs it.
- Sharing librime or MARISA's code with other modules at runtime: §5.4.1 links each into its side module.

## R19: the comparison

`tools/pinyin-compare/` (`@ibus-web/pinyin-compare`) runs one corpus through native ibus-libpinyin's library and native
librime with `rime-ice`, both from the pinned nixpkgs, and writes a report.

- **Corpus.** About 1,000 Mandarin sentences from Tatoeba, of 8 characters or more, converted to simplified with
  OpenCC's `t2s` and stripped of punctuation, Latin text and digits. Tatoeba's exports are replaced weekly, so the
  sample is committed (`tools/pinyin-compare/corpus.tsv`, CC-BY-2.0-FR, with its REUSE annotation and Tatoeba's sentence
  ids).
- **Input.** Each sentence as toneless pinyin without separators, from pypinyin, committed beside it. Its errors on
  characters with several readings are the same for both engines.
- **Conversion.** libpinyin: `pinyin_parse_more_full_pinyins`, `pinyin_guess_sentence`, then the sentence. Rime: the
  sentence's keys through `RimeProcessKey` on a `rime_ice` session, then the first candidate; if it covers only part of
  the input, it is selected and the next first candidate taken until the input is used up. Both with fresh user data.
- **Metrics.** Exact-sentence accuracy and character accuracy (1 minus the edit distance over the sentence's length),
  each over the whole corpus and by sentence length.
- **Outcome.** The report and its figures become R19's resolution in the design spec. If libpinyin is clearly ahead,
  more than either metric's 95 % confidence interval, the spec makes libpinyin M6, ahead of 1.0 as M7; otherwise R19
  closes and libpinyin stays dropped. M5 delivers Rime either way.

`packages.ibus-web-pinyin-compare-report` builds the report natively. It isn't a check: a score is a finding, not a pass
or a failure. `checks.tools-pinyin-compare` runs the tool's Vitest tests: corpus loading, normalisation, the metrics on
hand-made cases and the partial-candidate loop.

## Build

`engines/rime/` holds the port: `overlay.nix`, `module.nix`, the module's sources under `module/`, the descriptor
program, `patches/{port,casts}`, the cast-audit allow-lists and `checks/`. `flake.overlays.rime` applies only to
`pkgsWasm` and overrides nixpkgs' recipes, keeping their CMake builds.

### Dependencies

Each is nixpkgs' recipe, built static, private to the module:

- **LevelDB**, without its tests, benchmarks and `leveldbutil`. Its background compaction thread stays: unlike the
  existing WebAssembly ports of Rime (LibreService's `my_rime`, `fcitx5-prebuilder` for `fcitx5-js`), which run
  `PosixEnv::Schedule`'s work inline for want of threads, the runtime has them. If `rime-host` shows the thread
  misbehaving, the inline schedule is the fallback, at the cost of compaction during a keystroke.
- **yaml-cpp**, without its tools and tests.
- **OpenCC**, without its Jieba plugin, tools and tests; its conversion data is data, in the module's closure.
- **glog**, without gflags and libunwind. Logging stays on and goes to stderr (`log_dir` empty in Rime's traits), so it
  reaches the page as `Log` records.
- **Lua 5.4**, without `LUA_USE_DLOPEN`.
- **MARISA**, the one package the table engine also builds against. Its recipe and overlay move from `engines/table/` to
  `modules/marisa/`, shared infrastructure, with its upstream-test check; the native build the table tools link reaches
  them through an `ibusWeb.marisa` option. Each side module still links its own static copy.
- **Boost**, headers only; librime 1.17 needs no compiled Boost library.

Those two ports and their patches are references for what breaks. Both are AGPL-3.0; our patches are our own.

### librime

`librime` 1.17.0 is built static (`BUILD_STATIC`, `BUILD_SHARED_LIBS` off), with `BUILD_MERGED_PLUGINS` and nixpkgs'
default plugins, `librime-lua` and `librime-octagram`; `ENABLE_THREADING` stays on, so maintenance runs on the
deployer's `std::async` thread. Its tools (`rime_deployer`, `rime_dict_manager`) are built for WebAssembly as programs
too, for the build-time deployment. One port patch is expected beyond what the cast audit finds: the switcher filter
([Switches as properties](#switches-as-properties)).

### ibus-rime

`ibus-engines.rime` 1.6.1 contributes `rime_engine.c` and `rime_settings.c`, compiled with the flags its CMake build
uses and linked with librime, the dependencies and the module's sources into `rime.wasm`. `rime_main.c`, which connects
to the bus and shows desktop notifications, is not built, so neither is anything of libnotify, which only it uses; the
CMake build's requirement of it is patched out. Its port patches select the session's schema from the engine's name and
register the switches as properties.

### Deployment at build time

`rime_deployer --build`, built for WebAssembly, runs under Node over a merged data directory: `rime-data`,
`rime-loengfan`, then `rime-ice`, whose `double_pinyin*` schemas replace `rime-data`'s of the same names, and a
generated `default.yaml` whose `schema_list` is the shipped schemas. Its output becomes store paths of two kinds:

- **Common** (`ibus-web-rime-common`): the compiled schema and configuration YAML, `symbols`, the OpenCC data, and
  `rime-ice`'s Lua scripts. A few MB, the module's base data, and Rime's shared data directory.
- **One per dictionary** (`ibus-web-rime-dict-<dictionary>`): its `.table.bin`, `.prism.bin` and `.reverse.bin`, under a
  `build/` directory that Rime finds through a symbolic link from the common path's.

The compiled dictionaries come from the same librime that reads them. Whether a redeploy at runtime, which settings
cause ([Settings](#settings)), accepts the prebuilt tables when the shared directory holds no dictionary sources is the
first thing the build verifies (`rime-deploy`); if it doesn't, the sources go into the dictionary paths too.

## Startup

`ibusweb_module_init` does what ibus-rime's `main()` does without a bus:

1. fills `RimeTraits`: the shared data directory the common store path, compiled in; the user data directory
   `g_get_home_dir()`, which the host makes `/engines/<name>`; `log_dir` empty; the distribution name and version;
2. writes the YAML its settings generate ([Settings](#settings));
3. sets the notification handler, which on a deployment's success reloads ibus-rime's settings, as `rime_main.c`'s does,
   and logs where `rime_main.c` would show a notification;
4. calls `RimeSetup`, `RimeInitialize` and `RimeStartMaintenance(False)`, which checks the user directory against the
   shared one on the deployer thread, then deploys `ibus_rime.yaml` as `rime_main.c` does;
5. registers each shipped schema's engine type with the factory.

While maintenance runs, Rime's service is disabled and keys pass through unhandled, as on the desktop. The module lives
as long as its Worker; Rime's `RimeFinalize` is never reached, as Mozc's handler is never freed.

### Descriptors

The descriptor program, a WebAssembly program run under Node at build time like m17n's, reads each shipped schema's
deployed config through librime's API and prints its id, name, dictionary and `dependencies`, and its switches with
their states' labels. `descriptors.ts` (`@ibus-web/rime-descriptors`) turns that into the module's files:

| Descriptor field | Value                                                                                                                               |
| ---------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| `name`           | `rime:<schema_id>`                                                                                                                  |
| `displayName`    | The schema's name and an English gloss in parentheses, `雾凇拼音 (Pinyin, simplified)`; the glosses are a table in the module's Nix |
| `languages`      | From the same table                                                                                                                 |
| `keyboard`       | `{ layout: "us", passThrough: [] }`: the shape-based schemas map key positions                                                      |
| `data`           | The dictionary store paths of its schema and, transitively, of its dependencies' schemas                                            |

A schema without a gloss, or a dependency that isn't deployed, fails the build. `rime:rime_ice` comes first; the rest
follow the table's order.

Dependencies make some engines' data larger than their own dictionary: `rime_ice` brings `melt_eng` and
`radical_pinyin`, Cangjie and Quick bring `luna_pinyin` (through `luna_quanpin`, for reverse lookup by pinyin), and
Jyutping brings `luna_pinyin`, `loengfan`, `stroke` and `cangjie5`.

`loengfan` (`粵語兩分`, Cantonese input by the readings of a character's two parts) is CanCLID's, and `rime-data`
doesn't have it. `rime-loengfan`, a data-only derivation in the overlay, takes it from Debian's source package: the orig
tarball of `rime-loengfan` `0.0~git20220303.987ac95` (upstream commit `987ac95`, SHA-256 `e274750c…`), fetched from the
Debian pool with `snapshot.debian.org` as the fallback URL, since the pool drops superseded versions. It holds
`loengfan.schema.yaml`, a 1.7 MB `loengfan.dict.yaml` and its CC-BY-4.0 `LICENSE`, and depends only on `cangjie5`.

### Selecting schemas

The module's recipe, `engines/rime/_package.nix`, takes `extraSchemas ? [ ]`: further `rime-data` schema ids to deploy
and register beside the default set. Its `passthru.nicheSchemas` lists every `rime-data` schema the default set leaves
out, so one override builds them all:

```nix
ibus-web-rime-dist.override { extraSchemas = ibus-web-rime-dist.nicheSchemas; }
```

The schema list reaches everything built from it: the generated `default.yaml`'s `schema_list`, the deployment and its
dictionary store paths, the descriptors and the engine types the module registers. The gloss and language table covers
every `rime-data` schema, not only the default set, so an extra schema needs no other change; an id `rime-data` doesn't
deploy fails the build. The distribution and npm package built from the override carry the extra engines, each with its
own lazy data.

### Switches as properties

A port patch to ibus-rime registers the current schema's switches as IBus properties, keyed `rime:option:<name>`
(`rime:option:ascii_mode`, `rime:option:full_shape`, `rime:option:simplification`, …): a switch of two states is a
toggle; one of more, a group of radio properties keyed by each option's name. Labels are the schema's own state labels.
Rime's option notification sends `UpdateProperty`; `PropertyActivate` calls `RimeSetOption`. ibus-rime's existing
properties (its mode indicator, "Deploy", "Sync") stay.

A page that wants its own controls reads these from the `panel` events and sends `PropertyActivate` through the panel
action it already has, and doesn't place `panel.properties`; nothing on the page side changes for it. To take Rime's own
controls away, the settings empty `switcher-hotkeys` and set `ascii-toggle-key` to `none`.

Rime's switcher menu (F4, Ctrl+`) keeps its option items but lists only the engine's own schema: the page's picker is
the schema switcher, and switching inside Rime to a schema whose data this Worker hasn't installed would fail. A port
patch to librime filters the switcher's schema list through a predicate the module sets.

## Settings

Rime is configured by YAML patches in the user directory. The module takes its settings from GSettings, as Mozc does,
and writes the patches itself.

- **`org.freedesktop.ibus.engine.rime`**, fixed:
  - `page-size`;
  - `switcher-hotkeys`, a list of Rime key names, `["F4", "Control+grave"]` by default; empty turns the menu off;
  - `ascii-toggle-key`: `shift`, `caps-lock`, `control` or `none`, as Rime's `ascii_composer` offers them;
  - `inline-preedit`, `preedit-style` (`composition` or `preview`) and `cursor-type`, ibus-rime's own;
  - `traditional`, whether `rime-ice`'s engines start with `traditionalization` on;
  - `fuzzy-pinyin`, the fuzzy pairs `rime-ice` provides commented out in its speller, for its pinyin and double pinyin
    engines.
- **`org.freedesktop.ibus.engine.rime.schema`**, relocatable, at `/org/freedesktop/ibus/engine/rime/<schema_id>/` for
  each engine through M4's settings by path: the initial states of that schema's `full_shape`, `ascii_punct` and, where
  it has one, `simplification` switches.

At startup and on each `changed` signal the module writes `default.custom.yaml` (page size, switcher hotkeys, ASCII
composer), `ibus_rime.custom.yaml` (ibus-rime's display options) and each `<schema_id>.custom.yaml` (its switches'
resets and fuzzy pinyin), each only when its content differs. If one did, it starts maintenance, which recompiles the
affected configs into `/engines/<name>/build` on the deployer thread and reuses the prebuilt tables. Rime ends its
sessions to deploy, and ibus-rime makes a new one when it finds its own gone, so an open context takes the change up at
its next key after maintenance ends.

## Per-engine data

Today a module's whole data closure is installed before Init. M5 lets an engine name data of its own, installed before
it is first made.

### Manifest

`EngineDescriptor` gains `data?: string[]`, store paths from the module's `data`. An archive any engine names is lazy;
the rest are base data and install at start as now. `decodeModuleManifest` rejects a path not in `data`, and a lazy path
holding `settingsSchemaDir`. `mkEngineManifest` takes each engine's paths with its descriptors, as a Nix list or a JSON
file a derivation builds.

### Installing

- **Markers.** `meta.installed` records the base install as now. Each lazy path gets its own marker,
  `meta.paths/<storePath>`, `{ files, bytes }`, written after its archive is extracted. The version's database, its
  three locks and the collection of old versions are unchanged; lazy paths live in the same database.
- **The install window.** The data backend can no longer be sealed for good, since any host may later need to install a
  path. `wasmfs_idb_backend_set_writable(backend, writable)` gates it instead: a change while it isn't writable fails
  with `EROFS`, as a sealed backend's does. The host makes it writable only while it holds the version's install lock
  and runs the extractor. The engine's own files keep the one-way seal and the writer lock. An engine thread in the same
  Worker could write to `/nix/store` while the window is open; none does, and the window lasts one extraction. This is
  weaker than the seal, and the design spec says so.
- **`PrepareEngine`.** A Worker message, outside the ring and the request loop, as installing is: `{ engine }`. The host
  takes the install lock, reads each of the engine's lazy paths' markers, and for each missing one removes whatever an
  interrupted install left under it, opens the window, streams and extracts its archive with the existing checks (its
  own `size` limit; entries confined to its path), writes the marker, and closes the window. It reports progress while
  it works and an `install` report per path, then lets the lock go. With every marker present it does nothing; the files
  are already in the mounted database.
- **Other Workers.** A host that mounted the version before another installed a path finds it by lookup: WasmFS caches
  the entries it has found, never an entry's absence. The first task of the phase verifies this.
- **Memory mounts.** Without IndexedDB the data lives in WebAssembly memory, which is sized at start and can't grow, so
  such a host installs every archive at start, sized as now.

### Page

- `select(module, engine)` sends `PrepareEngine` before `CreateEngine` when the engine has lazy data, and waits for it.
- The facade gains `prepare(module, engine)`, which a page calls to fetch an engine's data ahead of selection, and an
  `install` event, `{ module, engine, bytes, total }`, while it runs. The demo shows it.
- A failed install fails the selection with a tagged reason, as a failed `CreateEngine` does.

For Rime, the base data is `ibus-web-rime-common`, and each dictionary path is lazy. Measured natively, the shipped
dictionaries come to 159 MB compiled, 62 MB as Brotli; `rime_ice` is 59 MB compiled, so a simplified-pinyin user
downloads about a third of it.

## Distribution

`ibus-web-rime-dist` is built by `mkEngineManifest` with `threads` and `heapBytes` from `rime-host`'s peaks plus several
MB. The threads expected are LevelDB's compaction thread, which lasts as long as the module, and the deployer's, during
maintenance. Rime maps its tables with `mmap`, which WasmFS serves as a copy in memory, so the break counts every
dictionary the workload has open: `rime_ice` with one traditional engine. The licence is the conjunction of librime's,
the plugins', the dependencies', ibus-rime's and the data's (`rime-data`'s four, `rime-loengfan`'s `CC-BY-4.0`,
`rime-ice`'s `GPL-3.0-only`). `packages/engines/rime/` is `@ibus-web/engine-rime`, packed by `npmTarball`, with each
licence text in `LICENSES/`.

## Delivery

Four phases, reviewed at the end of each:

1. **5a, the comparison.** `tools/pinyin-compare`, its corpus and report, and R19's resolution in the design spec, with
   libpinyin as M6 if it wins. Native only; it comes first because its result can change the roadmap.
2. **5b, Rime under Node.** The overlay and dependencies, `rime.wasm` and its init, the build-time deployment, the
   descriptor program, the switch properties and switcher filter, the settings schemas, and `rime-deploy`,
   `rime-golden`, `rime-userdb`, `rime-engines` and the cast audit. All data installs at start, through the existing
   mechanism.
3. **5c, per-engine data.** The manifest field, markers, the install window, `PrepareEngine`, the page's `prepare` and
   `install`, their tests with fixtures, then Rime's dictionaries made lazy and `rime-host` extended.
4. **5d, Rime in the browser.** The distribution and npm package, the demo and Playwright, the benchmark, and the docs:
   a new `docs/rime.md`; per-engine data in `docs/engines.md`, `docs/storage.md`, `docs/worker-host.md` and
   `docs/ibus-web.md`; the design spec's §5.6 (the install window), §10.2 (nixpkgs' Rime data; the NUR only when
   needed), R7 (resolved by per-engine data), its M5 row (settings through GSettings, not YAML through a storage API).

Phases 1 and 2 are independent. Phase 3's Rime part needs phase 2.
