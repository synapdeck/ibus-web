# M4: m17n

M4 ports ibus-m17n, the IBus front end of the m17n input-method library, as one engine module, `m17n`, with every
input method m17n-db provides that ibus-m17n would offer: some 190 engines in one Worker, for Indic, South-East Asian,
Vietnamese, Ethiopic, Cyrillic and many other scripts, plus a handful of general-purpose methods such as Latin postfix
diacritics.

Two things in the runtime and the page change for it. ibus-m17n opens its GSettings schema at a separate path for each
engine, so settings become addressed by path rather than by schema id, and relocatable schemas work end to end. And
ibus-m17n looks keys up in IBus's US keymap, so libibus-web gains a real one.

## Goals

- Every usable m17n input method typing in the browser, through the existing router and panel.
- An engine that reads and deletes surrounding text (Thai, the Indic methods that trim a halant) in a real port.
- Relocatable GSettings schemas: one schema at many paths, each instance's settings stored, synchronised and sent to
  the engine like any other.
- m17n's own per-input-method variables as ordinary settings.
- Many engines in one module, with their descriptors generated from the code that registers them.

## Non-goals

- m17n's GUI, font layout and text-property libraries: only the core and input-method libraries are built.
- Input methods that need a plugin loaded with `dlopen` (`ja-anthy`, `ispell`).
- Editing m17n's key bindings (`minput_config_command`) or its per-user customisation file. Variables are the only
  m17n configuration exposed.
- Variable changes reaching an open engine; they apply when the module next starts.
- Compose sequences. ibus-m17n chains to `IBusEngineSimple` for them, whose runtime implementation handles none.
- Large data sets. m17n-db is 7.8 MB; Mozc already loads a 54 MB set.

## Build

`engines/m17n/` holds the port: `overlay.nix`, `module.nix`, the module's C sources under `module/`, the descriptor
program, `patches/{port,casts}`, `cast-audit.jsonc` and `checks/`. `flake.overlays.m17n` applies only to `pkgsWasm`
and overrides nixpkgs' recipes, keeping their Autotools builds.

### m17n-lib

`m17n_lib` 1.8.6 is built static, with `--disable-gui` and without every optional library: fribidi, libotf,
freetype, Xft, fontconfig, gd, libxml2, anthy, libthai and wordcut. None of them is reached from input methods:
the GUI and font-layout libraries serve m17n's drawing, libxml2 its MText serialisation, and libthai and wordcut its
Thai word segmentation, whose only caller is the line breaker. The Thai input methods check character sequences in
their `.mim` source, through surrounding text. The build runs the `m17n-db` program, which comes from the build
machine through cross splicing.

### m17n-db

`ibus-web-m17n-db` is a data-only derivation holding the native `m17n_db` output's `share/m17n`: the input methods,
their icons, charset maps and tables, 7.8 MB in all. `bin/` and `scripts/` are left out, since their shell and awk
scripts would bring bash and gawk into the closure. The `M17NDIR` that m17n-lib compiles in is this derivation's
directory, so the data keeps its store path. m17n's per-user directory, `~/.m17n.d`, lies under the module's home,
`/engines/m17n`.

### ibus-m17n

`ibus-engines.m17n` 1.4.40 is built without GTK, Python and `wrapGAppsHook3`, configured `--without-gtk`. Upstream's
`libm17ncommon` and `engine.c` link with the module's sources into `m17n.wasm`; `main.c`, which connects to the bus, is
not built.

Port patches are expected to be few: dropping input methods that are listed but can't open here
([Engines](#engines)), and whatever the cast audit finds, in `patches/casts`.

## Startup

`ibusweb_module_init` does what ibus-m17n's `start_component` does without a bus:

1. calls `ibus_m17n_init_common()`, which initialises m17n;
2. applies the input-method variables from their settings ([Variables](#variables));
3. calls `ibus_m17n_get_component()`, which lists m17n's input methods and applies `default.xml`'s ranks and blacklist;
4. registers each listed engine's type, from `ibus_m17n_engine_get_type_for_name`, with the factory.

ibus-m17n opens an engine's input method in its class constructor, when the first context of that engine is created,
so the variables are in place before any input method opens.

## Engines

The engines are those `ibus_m17n_list_engines` keeps: input methods that load, that `default.xml` doesn't rank below
zero (`zh:py`, `ja:anthy`, `ko:han2`, `ko:romaja`), and whose candidate charset UTF-8 can encode. `ja:anthy` and the
`ispell` method need a plugin through `dlopen`; if ibus-m17n still lists either, a port patch drops it from
`ibus_m17n_list_engines`, which the module and the descriptor program share. Each engine keeps upstream's name,
`m17n:<lang>:<name>`.

### Descriptors

`engines/m17n/descriptors.c` is a WebAssembly program, run under Node at build time, linked with the same m17n-lib,
`libm17ncommon` and libibus-web as `m17n.wasm`. It calls `ibus_m17n_init_common()` and `ibus_m17n_get_component()`
and prints, for each engine description, its name, language, rank and layout, and the input method's variables
(below). A TypeScript step turns that into three files: the engine descriptors for `mkEngineManifest`, the settings
paths of ibus-m17n's relocatable schema, and the variable schemas. The module and its manifest therefore list the same
engines from the same code.

| Descriptor field | Value                                                                                                                                  |
| ---------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| `name`           | The engine's name                                                                                                                      |
| `languages`      | m17n's language, an ISO 639 code and so BCP 47 (`hi`, `sat`, `new`); `[]` for the `t:*` methods                                        |
| `displayName`    | The language's English name from `Intl.DisplayNames` and the method in parentheses, "Hindi (inscript)"; the bare method name for `t:*` |
| `keyboard`       | `{ layout: "default", passThrough: [] }`                                                                                               |

m17n's `title` is the mode indicator (क for `hi:inscript`), not a name, so it doesn't serve as the display name.
Upstream's `default[lv3:ralt_switch]` layouts become `default`. A user who wants keys taken from their US positions
turns on the engine's `use-us-layout` setting, which works through the runtime's US keymap.

Engines are sorted by language, then name. The first, the module's default, is a module option set to
`m17n:t:latn-post`, Latin postfix diacritics, which works on any keyboard.

## Settings by path

A setting's address becomes its path and key, as in dconf; the schema id describes what lives at a path. ibus-m17n
opens the relocatable schema `org.freedesktop.ibus.engine.m17n` at `/org/freedesktop/ibus/engine/m17n/<lang>/<name>/`
for each engine (`lookup-table-orientation`, the preedit colours and underline, `use-us-layout`).

### Metadata

`settings.json` describes each schema once, with its keys and `paths`, the paths it lives at. A fixed schema's one
path still comes from GLib. A relocatable schema's paths are the build's: `mkEngineManifest` takes `settingsPaths`, a
schema id to a list of paths or to a JSON file a derivation builds. Paths are unique across the file. The metadata tool
fails on a relocatable schema without paths and on paths given for a fixed one. The manifest's `settingsSchemas` stays
a list of schema ids.

### Protocol

The signatures are unchanged; what they carry is not.

| Message          | Signature       | Fields                                                                                   |
| ---------------- | --------------- | ---------------------------------------------------------------------------------------- |
| `Init`           | `(ua(ssa{sv}))` | protocol version; one entry per instance: schema id, path, that instance's stored values |
| `SettingChanged` | `(ssv)`         | path, key, value                                                                         |
| `SettingWritten` | `(ssv)`         | path, key, value                                                                         |

`Init` lists every instance the module's metadata declares, with an empty dictionary where nothing is stored, so the
runtime can map an engine's write to its schema.

### Runtime

`settings.c` builds an instance table from `Init`, path to schema. A fixed schema's instance must be at its own path;
a relocatable one's at a canonical path (absolute, ending in `/`, no empty component). `SettingChanged` looks its key
up by path. An engine's write is matched to the longest declared path that prefixes its key. An unknown schema, a fixed
schema at another path, a non-canonical path, and a write under no declared path are each refused with a `Log`
warning. `-ENOTSUP` remains only for a default settings backend other than the runtime's.

### Page

- `SettingsSnapshot` is keyed by path, then key. `SettingsChange` is `{ path, key, value, origin? }`.
  `SettingsSource.read(path, key)` and `snapshot(paths)` take paths.
- The IndexedDB persister and the `ibus-web:gsettings` broadcast already key by path. The persister's map from schema
  id to schema becomes one from path to instance; a change still reaches every module that declares its path, as
  `org.freedesktop.ibus.panel`'s does.
- The registry forwards a change to each live module whose metadata declares its path.
- The settings API, in core and the facade: `schemas(module)` returns each schema with its paths; `get(module, path,
key)`, `set(module, path, key, value)` and `reset(module, path, key)`. The panel reads its orientation at the panel
  schema's path.

### Variables

41 of m17n-db's input methods declare variables (`candidates-group-size`, `trim-last-halant`, `tone-mark-on-last`,
`use-surrounding-text`, …). The descriptor program reads each engine's with `minput_get_variable(lang, name, Mnil)`,
and for each input method that has any, the TypeScript step writes a fixed-path schema,
`org.freedesktop.ibus.engine.m17n.<lang>.<name>`, at `/org/freedesktop/ibus/engine/m17n/<lang>/<name>/variables/`:

| m17n type | Key type | Constraint                      |
| --------- | -------- | ------------------------------- |
| integer   | `i`      | the declared range, if any      |
| symbol    | `s`      | the declared symbols as choices |
| text      | `s`      | none                            |

Defaults and descriptions come from the input method. A variable whose name isn't a valid GSettings key fails the
build. The schemas compile with ibus-m17n's and the panel's into the module's schema directory, and reach the page as
any schema does.

`engines/m17n/module/variables.c` reads every variable schema at module init and calls `minput_config_variable` with
each key's value. On a `changed` signal it does so again, but m17n applies a variable only to input methods opened
afterwards, and ibus-m17n opens each engine's once, so a change takes effect when the module next starts.
`minput_save_config` is never called: the page's settings are the only store, and `~/.m17n.d/config.mic` is never
written.

## The US keymap

`ibus_keymap_get("us")` returns a shared `IBusKeymap`, with a reference for each call; any other name returns `NULL`.
`ibus_keymap_lookup_keysym(keymap, keycode, state)` maps an evdev code and modifier state to the US keyval, and returns
`IBUS_VoidSymbol` for a `NULL` keymap or an unknown code.

The table comes from the JSON export of xkeyboard-config's US layout that `tools/keysyms` already turns into the page's
`us.generated.ts`. The same tool writes `runtime/libibus-web/src/ibus/us-keymap.generated.h`, a tracked generated file
with a `files:` check and xkeyboard-config's notice. Lookup follows the page's rules: NumLock alone selects keypad
levels, Shift and Lock invert each other for letters, and Shift selects the second level for other keys. Mod5 is
ignored; ibus-m17n clears it before asking.

libibus-web also gains `ibus_engine_simple_add_table_by_locale`, which loads nothing and returns `FALSE`.

## Distribution

`ibus-web-m17n-dist` is built by `mkEngineManifest` with `threads = 0` and `heapBytes` from the measured peak plus
several MB. Its data closure is `ibus-web-m17n-db` and the compiled schemas: ibus-m17n's, the variable schemas and
`org.freedesktop.ibus.panel`. Its licence is `GPL-2.0-or-later AND LGPL-2.1-or-later`. `packages/engines/m17n/` is
`@ibus-web/engine-m17n`, packed by `npmTarball`, with each licence text in `LICENSES/`.

## Delivery

Three phases, reviewed at the end of each:

1. **Settings by path and the keymap.** Relocatable settings across the protocol, runtime, metadata tool and page; the
   US keymap; `ibus_engine_simple_add_table_by_locale`. Tested with fixtures, without m17n.
2. **m17n under Node.** The overlays, `ibus-web-m17n-db`, `m17n.wasm` and its init, the descriptor program and its
   three outputs, `variables.c`, and `m17n-golden`, `m17n-engines` and the cast audit.
3. **m17n in the browser.** The distribution and npm package, `m17n-host`, the demo and Playwright, and the docs: a new
   `docs/m17n.md`, `docs/engines.md`, `docs/runtime.md`, `docs/core.md`, `docs/known-gaps.md` (variable changes wait
   for a restart), the design spec's §5.2.5, §6.1.3, §7.1.4 and its M4 row, whose questions become surrounding text,
   relocatable settings and many engines in one module.

Phase 2 can start before phase 1 ends; its settings work needs phase 1.
